# Автономність PWA та надійність даних

Досліджено 23 жовтня 2026 року. **Повністю офлайн-запускати довільні ігри поточна версія ще не може.** Профілі, JAR, налаштування, RMS, ручні слоти та історія зберігаються локально; сервер не є сховищем цих даних.

## Що перевірено фактично

На `https://retrojava.pp.ua` у чистому Chromium запущено власний RMS Probe, дочекалися `PROBE_READ:0`, потім штатно зупинили гру. Під час запуску зафіксовано **113 відповідей ресурсів рушія, 82 запити з Range**; зовнішній runtime завантажувався з `cjrtnc.leaningtech.com`. Це вимір одного MIDlet, а не розмір чи повний список залежностей усіх ігор.

Після вимкнення мережі та перезавантаження бібліотека відкрилася через service worker. Для діагностики лише в тестовому браузері обійдено ранню перевірку `navigator.onLine`: новий iframe `/engine/player.html?token=…` не завантажився з `ERR_INTERNET_DISCONNECTED`. Production-перевірка мережі залишена: користувач одразу отримує пояснення замість очікування таймауту.

Це підтверджує поточну межу офлайн-режиму. Навіть кешування всіх локальних `/engine/*` саме по собі ще не довело б автономність JVM: потрібні також її зовнішні залежності.

## Чому кешу першого запуску недостатньо

CheerpJ довантажує частини Java runtime на вимогу. Один пройдений екран гри не гарантує, що наступний рівень, звук, інша мова чи 3D не потребуватимуть нового ресурсу. `preloadResources` прискорює завантаження відомих залежностей; це не підтвердження повноти офлайн-пакета. Джерела: [офіційний FAQ](https://cheerpj.com/docs/faq), [resource preloading](https://cheerpj.com/docs/guides/Startup-time-optimization.html).

У виміряному запуску CDN повертав CORS `*`, але також використовувалися часткові відповіді. Для керованого офлайн-кешу потрібні окрема реалізація Range, перевірка цілісності, повний перелік ресурсів, обмеження розміру, обробка нестачі місця й узгоджені версії. Офлайн-збереження отриманих CDN-відповідей в браузері технічно відрізняється від розміщення runtime на власному сервері; тут не робиться висновку, що будь-який браузерний кеш заборонений ліцензією.

Офіційна Community License описує використання з CDN. Самостійне розміщення та розповсюдження CheerpJ потребують відповідних комерційних прав. Публічна production PWA не є закритою технічною оцінкою. Джерело: [CheerpJ Licensing](https://cheerpj.com/docs/licensing). Платну ліцензію не придбано, runtime на сервер не скопійовано.

| Шлях                                                                 | Що потрібно                                                                                                                      | Межа поточного дослідження                                                                                                    |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |

Сам self-hosting не робить PWA автономною на телефоні |
| Окремий локальний J2ME/JVM-рушій                                     | Прототип адаптера, локальні ресурси, повторна перевірка LCDUI, RMS, MIDI, M3G, Mascot і швидкодії на iPhone                      | Заміна рушія є окремою розробкою; збереження FreeJ2ME не можна вважати бінарно сумісними без тестів                           |
| Кешувати лише вже використані CDN-ресурси                            | Дослідний кеш окремих ігор і Range-запитів, перевірка ліцензійних умов такого пакування                                          | Може допомогти конкретним сценаріям, але не доводить повну автономність довільних JAR                                         |

Серед відкритих основ досліджено [Mozilla PluotSorbet](https://github.com/mozilla/pluotsorbet), J2ME JVM на JavaScript: оригінальний репозиторій архівований у 2018 році. [Doppio](https://github.com/plasma-umass/doppio) — JVM на TypeScript; це потенційна основа, а не готова заміна нашої FreeJ2ME-інтеграції. [TeaVM](https://www.teavm.org/docs/intro/overview.html) компілює bytecode наперед і обмежує class loaders/reflection: просте перезбирання FreeJ2ME через TeaVM не забезпечує завантаження довільного JAR на пристрої. Висновок про потрібну інтеграцію — інженерна оцінка; жоден із цих варіантів у production не підмінявся й сумісність ігор на них не заявляється.

Окремо перевірено сучасний [Rosabis/J2meJS](https://github.com/Rosabis/J2meJS): його поточний README заявляє заборону модифікації та розповсюдження. Публічний репозиторій не робить цей варіант вільним для включення до нашої PWA; код або збірки звідти не додавалися.

## Реалізований захист даних

- Наявна IndexedDB `java-retro-v1` зберігає свою назву. Міграція схеми v2 → v3 додає таблицю автокопій без очищення профілів, JAR чи RMS.
- Для записів використовується `durability: strict` через Dexie. Це запит до браузера на посилену довговічність транзакцій, а не гарантія від апаратної несправності. [IDBTransaction.durability](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/durability).
- Нове RMS перевіряється перед записом. Оновлення поточного запису й ротація двох попередніх версій виконуються однією транзакцією. Відмова, зокрема через квоту, відкочує всю транзакцію. Старі дані не видаляються заради запису нових.
- Однаковий вміст RMS не створює нових автокопій через зміну часових полів ZIP. Це також зменшує кількість записів.
- Плеєр показує `RMS ✓ час` після підтвердження запису базою або перевірки незміненої збереженої копії. Помилка позначається окремо. Час означає підтвердження копії на пристрої; це не обіцянка, що гра вже записала весь свій прогрес у RMS.
- Залишено копіювання раз на 3 секунди та фінальний запис через «Стоп». При приховуванні/закритті вікна запитується додаткова копія, але ОС може призупинити JavaScript раніше завершення. Цей запит не замінює штатний «Стоп».
- Постійне сховище запитується при створенні профілю й запуску встановленої PWA; результат та приблизний обсяг показуються в налаштуваннях. Відмова або відсутність API не видаються за дозвіл й не блокують профіль.
- Вибраний ID профілю пам’ятається між запусками. Дані профілю залишаються в IndexedDB, а не в цьому покажчику.
- Експорт профілю читає узгоджений знімок даних однією транзакцією. ZIP містить JAR, конфігурацію, поточне RMS, ручні слоти й історію. Дві автоматичні попередні версії залишаються локально; їх можна експортувати окремо.

Відновлення: **гра → «Збереження» → «Автоматичні попередні копії»**, після зупинки гри. Перед відновленням поточна версія також потрапляє в ротацію. Автокопії займають до двох додаткових RMS-архівів на гру й мають спільну квоту браузера.

## Що означає надійне зберігання на iPhone

WebKit підтримує Storage API з Safari/iOS 17; дозвіл `persist()` залежить від евристик, зокрема запуску з домашнього екрана. PWA не може самостійно нав’язати дозвіл. Квота є оцінкою, а не обсягом гарантовано вільного місця. [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/).

Звичайна вкладка Safari й Home Screen PWA можуть відрізнятися політикою збереження; не слід покладатися на спільність їхніх даних. Використовуйте один встановлений застосунок та незмінний HTTPS-домен. WebKit окремо пояснює, чому його правило семи днів Safari не слід автоматично переносити на активне використання Home Screen PWA: [ITP і Home Screen web apps](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/).

Постійне сховище знижує ризик автоматичного видалення браузером. Воно не захищає від ручного очищення, видалення застосунку, приватного режиму, скидання, втрати чи поломки пристрою. Інша локальна база або OPFS на тому самому origin також не є незалежною копією. [Квоти та очищення сховищ](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

Для відновлення після очищення потрібен **ZIP поза браузером**: «Налаштування» → «Експорт профілю» → зберегти у «Файлах», за потреби в iCloud Drive чи на іншому носії. Завантаження файла у тесті перевіряє його вміст; застосунок не може підтвердити, що користувач зберіг його у вибраному місці. Автоматичне фонове створення довільних файлів у «Файлах» на iOS тут не заявляється.

## Критерії готовності повного офлайн-режиму

1. Завантажити і перевірити **весь** потрібний пакет, показати його версію та завершення підготовки; частковий пакет не отримує статус «готово».
2. Повністю закрити браузер/PWA, увімкнути авіарежим і заново відкрити зі значка.
3. Запустити кілька різних дозволених JAR, перейти між рівнями, перевірити MIDI, LCDUI, потрібні 3D API; перевірити відсутність залежності від мережі.
4. Зберегти RMS, закрити процес, повторно відкрити без мережі й прочитати прогрес.
5. Перевірити недостатню квоту, обірване завантаження пакета, оновлення, відкат і збереження бази попередньої версії.
6. Повторити на фізичному iPhone у встановленій PWA та Android. Chromium viewport або WebKit на Windows не замінюють перевірку iOS.

Автоматизовано зараз: міграція v2, атомарне відкочування при помилці запису, ротація й дедуплікація копій, чужі профілі, відмова/відсутність Storage API, повторний запуск браузера без мережі, відновлення RMS та офлайн-експорт/імпорт ZIP. Повна офлайн-JVM та фізичний iPhone **не пройшли** ці критерії й не заявляються реалізованими.
